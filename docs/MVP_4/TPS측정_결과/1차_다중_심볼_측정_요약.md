# 1차 다중 심볼 측정 요약

## 1. 측정 목적

Phase 4 구현 직후 다중 심볼 주문 부하에서 심볼 분산 효과와 안정 처리 가능한 TPS 구간을 확인한다.

이번 1차 측정은 다음에 집중했다.

* `BTC`, `ETH`, `TEST` 3개 심볼로 주문 부하를 분산했을 때 안정 처리량 확인
* 단일 심볼 대비 queue backlog 발생 시점 비교
* DB/락 병목 여부와 심볼별 엔진 큐 분산 효과 분리

---

## 2. 측정 조건

애플리케이션/환경:

* Spring Boot `perf` profile
* PostgreSQL 연동
* Prometheus + Grafana 연동
* 심볼: `BTC`, `ETH`, `TEST`

데이터 조건:

* account 100개 seed
* account당 충분한 잔고 주입
  * `KRW 1,000,000,000,000`
  * `BTC 1,000,000`
  * `ETH 10,000,000`
  * `TEST 1,000,000,000`

부하 시나리오:

* k6 `scripts/k6/scenarios/place-multi-symbol.js`
* `SYMBOLS=BTC,ETH,TEST`
* `MIN_PRICE=99,000,000`
* `MAX_PRICE=101,000,000`
* `MIN_QTY=1`
* `MAX_QTY=1`
* `VUS` 와 `SLEEP_SECONDS` 값을 조정하며 안정 구간과 임계점 구간을 탐색

판정 기준:

* 안정 구간
  * `engine_backpressure_count = 0`
  * `queue_full_rollback_count = 0`
  * 모든 심볼의 `engine_queue_depth = 0`
  * `queue_wait_latency p95` 가 ms 수준에서 유지
* 비안정 구간
  * 심볼별 `engine_queue_depth` 누적
  * `queue_wait_latency p95` 급등
  * `end_to_end_order_latency p95` 급등
  * backpressure 또는 queue rollback 발생

---

## 3. 주요 측정 결과

### 3.1 안정 구간

대표 안정 구간은 `VUS=2`, `SLEEP_SECONDS=0.001` 로 확인됐다.

주요 수치:

* `place_order_tps`: `266.64/s`
* `accepted_order_tps`: `266.73/s`
* `trades_per_sec`: `104.33/s`
* `matched_orders_per_sec`: `208.72/s`
* `queue_wait_latency p95`: `3.06ms`
* `engine_processing_latency p95`: `7.31ms`
* `order_accept_tx_latency p95`: `2.22ms`
* `engine_result_tx_latency p95`: `5.45ms`
* `end_to_end_order_latency p95`: `11.33ms`
* `db_lock_wait_time p95`: `1.68ms`
* `engine_queue_depth`
  * `BTC=0`
  * `ETH=0`
  * `TEST=0`
* `engine_backpressure_count`: `0`
* `queue_full_rollback_count`: `0`

해석:

* 3개 심볼에 부하가 분산된 상태에서도 backlog 없이 안정적으로 처리 가능한 구간이다
* DB 락/트랜잭션 지연은 낮은 수준으로 유지됐다
* 현재 환경 기준 다중 심볼 안정 처리량은 최소 `260+ orders/sec` 수준으로 판단한다

### 3.2 backlog 시작 구간

`VUS=2`, `SLEEP_SECONDS=0` 에서는 backlog 누적이 시작됐다.

주요 수치:

* `place_order_tps`: `323.31/s`
* `accepted_order_tps`: `323.41/s`
* `trades_per_sec`: `124.74/s`
* `matched_orders_per_sec`: `249.48/s`
* `queue_wait_latency p95`: `422.56ms`
* `engine_processing_latency p95`: `8.68ms`
* `order_accept_tx_latency p95`: `2.34ms`
* `engine_result_tx_latency p95`: `6.18ms`
* `end_to_end_order_latency p95`: `426.81ms`
* `db_lock_wait_time p95`: `1.74ms`
* `engine_queue_depth`
  * `BTC=83`
  * `ETH=81`
  * `TEST=73`
* `engine_backpressure_count`: `0`
* `queue_full_rollback_count`: `0`

해석:

* backpressure는 아직 발생하지 않았지만 세 심볼 모두 queue backlog가 누적되기 시작한 구간이다
* `queue_wait_latency` 와 `end_to_end_order_latency` 가 함께 상승했다
* steady state가 아니라 backlog 누적 상태로 본다

### 3.3 단일 심볼 대비 비교

같은 1차 측정 기준에서 단일 심볼과 비교하면 차이가 명확했다.

단일 심볼:

* 안정 처리량: 약 `85~90 orders/sec`
* backlog 시작: 약 `130+ orders/sec`

다중 심볼:

* 안정 처리량: 최소 `260+ orders/sec`
* backlog 시작: 약 `320+ orders/sec`

해석:

* 현재 구조에서는 단일 hot symbol 부하보다 다중 심볼 분산 부하에서 훨씬 높은 처리량을 안정적으로 소화한다
* 심볼별 엔진 runtime 분산 효과가 크게 관찰된다

## 4. 병목 해석

이번 1차 다중 심볼 측정에서도 1차 병목은 DB보다는 심볼별 엔진 큐 소비 한계 쪽에 가깝다.

근거:

* backlog 시작 구간에서도 `engine_processing_latency`, `engine_result_tx_latency`, `db_lock_wait_time` 은 낮게 유지됐다
* `db_deadlock_count = 0`
* `db_commit_failure_count = 0`
* `db_rollback_count = 0`
* 반면 `queue_wait_latency` 와 `end_to_end_order_latency` 가 함께 증가했고, 모든 심볼에서 `engine_queue_depth` 가 증가했다

정리하면 다음과 같다.

* 현재 구조에서는 심볼이 분산되면 단일 심볼 대비 훨씬 높은 처리량을 유지할 수 있다
* 다만 전체 입력이 더 증가하면 심볼별 큐 backlog가 다시 병목으로 드러난다
* DB 락/트랜잭션 병목은 이번 1차 측정 구간에서는 주요 원인으로 관찰되지 않았다

---

## 5. 1차 결론

현재 환경과 시나리오 기준 1차 결론은 다음과 같다.

* 다중 심볼 안정 처리량은 최소 `260+ orders/sec`
* 약 `320+ orders/sec` 부근부터 각 심볼 queue backlog가 발생한다
* 단일 심볼 안정 처리량 `약 85~90 orders/sec` 대비 다중 심볼 분산 시 약 `3배` 수준의 안정 처리량 개선이 관찰됐다

따라서 Phase 4 1차 기준선은 다음처럼 기록한다.

* 다중 심볼 안정 TPS 기준선: `약 260+ orders/sec`
* backlog 진입 구간: `약 320+ orders/sec`
* 주요 병목 형태: `DB 락`보다는 `심볼별 엔진 큐 backlog 누적`
* 구조적 시사점: `hot symbol` 집중보다 `심볼 분산` 환경에서 훨씬 유리
