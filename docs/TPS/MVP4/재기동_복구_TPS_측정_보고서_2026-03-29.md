# MVP4 재기동 복구 TPS 측정 보고서

작성 시각: 2026-03-29T01:39:53Z

## 1. 목적

`docs/MVP_4/TPS_측정_계획.md`의 4.9 시나리오 기준으로, open order가 적재된 상태에서 서버 재기동 후 replay 복구 시간과 일관성을 확인했다.

이번 측정의 목적은 다음과 같다.

1. 재기동 직후 replay가 정상 완료되는지 확인한다.
2. orphan `ACCEPTED` 주문이 남지 않는지 확인한다.
3. 복구 후 오더북과 상태 일관성이 유지되는지 확인한다.

## 2. 측정 조건

- 대상: 단일 심볼 open order 약 `10000건`
- 측정 방식:
  1. open order가 적재된 상태에서 서버 종료
  2. 서버 재시작
  3. replay 메트릭과 consistency check 확인

주의:

- `replay_restored_order_count`는 실제 복구된 주문 수를 의미한다.
- `replay_orphan_cancelled_count`는 replay 과정에서 orphan `ACCEPTED` 상태로 발견되어 정리된 주문 수를 의미한다.
- `replay_duration_on_startup_p95_ms`는 전체 startup replay 시간의 대표값으로 사용했다.

## 3. 측정 결과

| 지표 | 값 | 해석 |
|---|---:|---|
| `replay_duration_on_startup_p95_ms` | `110.72962495 ms` | 재기동 후 replay가 약 110.73ms 내에 완료 |
| `replay_orphan_cancelled_count` | `0` | orphan `ACCEPTED` 주문 없음 |
| `replay_restored_order_count` | `10136` | replay를 통해 복구된 주문 수 |
| `replay_consistency_check` | `BTC=1`, `ETH=1`, `TEST=1` | 복구 후 상태 일관성 정상 |
| `replay_duration_by_symbol_p95_ms` | `TEST=3.82729975`, `ETH=5.52249995`, `BTC=NaN` | 심볼별 replay 시간 보조 지표 |

## 4. 해석

- 단일 심볼 open order 약 `10000건`이 존재하는 상태에서 replay가 정상 수행되었다.
- `replay_restored_order_count=10136`으로 복구 대상 주문이 실제로 존재했음이 확인되었다.
- `replay_orphan_cancelled_count=0`이므로 재기동 시 orphan `ACCEPTED` 주문 정리 이슈는 관찰되지 않았다.
- `replay_consistency_check`가 모든 심볼에서 `1`로 집계되어 복구 후 오더북/상태 일관성이 유지되었다.

`replay_duration_by_symbol_p95_ms`의 `BTC=NaN`은 심볼별 p95 표본 집계 방식 영향으로 볼 수 있으므로, 본 측정에서는 전체 replay 시간과 restored count, consistency check를 더 중요한 결과로 본다.

## 5. 결론

이번 실험 기준 재기동 복구 시나리오의 결과는 다음과 같이 정리한다.

- 단일 심볼 open order 약 `10000건` 복구 시간: 약 `110.73ms`
- 복구된 주문 수: `10136`
- orphan `ACCEPTED` 정리 수: `0`
- 복구 후 일관성 검증: 정상

보고서용 결론 문장:

> 단일 심볼 open order 약 10000건이 존재하는 상태에서 재기동 후 replay_duration_on_startup_p95_ms는 110.73ms로 측정되었고, replay_restored_order_count는 10136건이었다. replay_orphan_cancelled_count는 0이었으며, replay_consistency_check는 BTC/ETH/TEST 모두 1로 집계되어 복구 후 상태 일관성이 유지됨을 확인했다.

## 6. 시사점

- 현재 구현에서는 단일 심볼 10000건 수준의 open order replay가 매우 짧은 시간 안에 완료되었다.
- orphan `ACCEPTED` 정리 없이도 정상 복구가 가능했으므로, persisted 상태와 replay 경로의 일관성은 양호한 편이다.
- 추가 측정이 필요하다면 `1000건`과 `10000건`을 함께 비교해 replay 시간의 증가 추세를 확인하는 정도면 충분하다.
