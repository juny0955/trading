# MVP4 단일 심볼 BTC TPS 측정 보고서

작성 시각: 2026-03-26T11:56:43Z

## 1. 목적

`docs/MVP_4/TPS_측정_계획.md`의 4.2 단일 심볼 측정 시나리오 기준으로, BTC 단일 심볼에서 주문 처리량과 큐 병목 발생 지점을 확인했다.

이번 측정의 목적은 다음 두 가지다.

1. 단일 심볼 BTC에서 큐 적체 없이 유지되는 안정 처리량 범위를 확인한다.
2. 큐 포화, backpressure, lock contention이 어느 구간에서 발생하는지 확인한다.

## 2. 측정 조건

- 시나리오: `scripts/k6/scenarios/place-single-symbol.js`
- 심볼: `BTC`
- VU: `1`
- 측정 window: `300s`
- account 분포: seed account 사용
- 비교 변수: `SLEEP_SECONDS`

실행 예:

```bash
k6 run -e SYMBOL=BTC -e VUS=1 -e SLEEP_SECONDS=0.01 -e SCENARIO_NAME=place-single-symbol \
  scripts/k6/scenarios/place-single-symbol.js
```

## 4. 해석

### 4.1 `SLEEP_SECONDS=0.002`

- `place_order_tps`는 164.51까지 올라갔지만 실제 수용 처리량은 125.16 TPS였다.
- `engine_queue_depth: BTC=10000`으로 큐가 가득 찼다.
- `engine_backpressure_count`와 `queue_full_rollback_count`가 모두 39.35/s로 발생했다.
- 이 구간은 시스템 최대 투입량이 아니라, 이미 큐 포화 후 롤백이 섞인 상태다.

### 4.2 `SLEEP_SECONDS=0.005`

- 롤백은 사라졌지만 `queue_wait_latency_p95_ms=30000`, `engine_queue_depth: BTC=7011`로 적체가 계속 누적되었다.
- 즉, "롤백 없는 최대 주입 속도"에 가깝고 안정 상태는 아니다.

### 4.3 `SLEEP_SECONDS=0.007`

- 처리량은 89.34 TPS까지 올라갔다.
- 하지만 `queue_wait_latency_p95_ms=11795.96`, `end_to_end_order_latency_p95_ms=11809.93`, `engine_queue_depth: BTC=1688`로 큐가 계속 밀렸다.
- 롤백은 없지만 포화 직전 상태로 판단한다.

### 4.4 `SLEEP_SECONDS=0.010`

- `accepted_order_tps=66.42`
- `queue_wait_latency_p95_ms=0.97`
- `end_to_end_order_latency_p95_ms=15.11`
- `engine_queue_depth: BTC=0`
- `engine_backpressure_count=0`
- `queue_full_rollback_count=0`

이 구간은 큐 적체 없이 처리되는 첫 번째 안정 상태로 볼 수 있다.

## 5. 결론

이번 실험 기준 단일 심볼 BTC의 결과는 다음과 같이 정리한다.

- 안정 처리량: 약 `66 TPS`
- 포화 직전 구간: 약 `89 TPS`
- 큐 포화 및 롤백 발생 구간: 약 `125 TPS` 이상 수용 시도, 약 `164 TPS` 투입 구간

보고서용 결론 문장:

> 단일 심볼(BTC) 조건에서 약 66 TPS에서는 큐 적체 없이 안정 처리되었고, 약 89 TPS부터는 queue full rollback 없이도 engine queue depth와 p95 latency가 급증하여 포화 직전 상태를 보였다. 
> 약 125 TPS 이상을 수용하려는 구간에서는 queue full rollback이 발생하며 안정 처리량으로 보기 어렵다.

## 6. 시사점

- 병목은 DB 오류보다 단일 심볼 엔진 큐 적체에 먼저 나타났다.
- `balance_lock_contention_count`가 모든 구간에서 높게 유지되어 account/balance 경합도 같이 관찰된다.
- `engine_processing_latency_p95_ms` 자체는 13.84~22.44ms 범위로 상대적으로 안정적이었다.
- 따라서 체감 성능 악화의 주원인은 엔진 처리 시간보다 queue wait 증가였다.
