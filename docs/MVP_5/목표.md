# Trading Exchange Engine - MVP Phase 5 목표

## 0. 범위 고정

> Phase 5는 Phase 4의 영속성 기반 거래 시스템 위에 운영 관측성, 이벤트 전달, 실시간 클라이언트 인터페이스, FOK/IOC 성능 최적화를 얹는 단계다.
> 핵심은 **Outbox 전달 보장 / WebSocket 실시간성 / sequence 기반 복구 / 운영 메트릭 / 성능 개선**이다.

- [ ] Transactional Outbox 도입
- [ ] symbol 단위 `event_sequence` 도입 및 재시작 복구
- [ ] STOMP 기반 WebSocket 실시간 스트리밍 도입
- [ ] Snapshot + Delta + Gap Recovery 계약 고정
- [ ] Outbox / WebSocket / FOK-IOC 관련 운영 메트릭 추가
- [ ] FOK/IOC 가용 수량 계산 최적화
- [ ] 엔진 계산 레이어 순수화 마무리

### 제외 범위

- [ ] 외부 메시지 브로커(Kafka, RabbitMQ) 연동
- [ ] 다중 노드 분산 매칭 및 leader election
- [ ] 정식 JWT 기반 WebSocket 인증
- [ ] 차트 집계 엔진 / Candlestick 저장
- [ ] 관리자용 백오피스 UI

---

## 1. 선결정 항목 고정

- [ ] Outbox 전달 보장 수준은 `at-least-once`로 고정
- [ ] Outbox는 `MATCHING_RESULT_BUNDLE` 1건을 기본 저장 단위로 사용
- [ ] WebSocket 전송은 bundle 1건을 topic별로 fan-out 하는 방식으로 고정
- [ ] fan-out 하위 전송은 동일 `eventId`, `symbol`, `sequence`를 공유
- [ ] fan-out 하위 topic 중 하나라도 실패하면 bundle 전체 publish 실패로 간주하고 전체 재시도
- [ ] claim 상태는 별도 `SENDING` status 없이 `PENDING + next_retry_at` lease 방식으로 표현
- [ ] worker claim은 운영 환경에서 `SELECT ... FOR UPDATE SKIP LOCKED` 사용
- [ ] `event_sequence`는 `accepted_seq`와 별개인 심볼별 단조 증가 값으로 고정
- [ ] `event_sequence`의 Source of Truth는 `symbol_states.last_event_sequence`
- [ ] 재시작 시 `symbol_states`에서 최신 sequence를 읽어 발급 재개
- [ ] 거래 심볼 Source of Truth는 `application.yml` 리스트가 아니라 `symbols` 테이블로 고정
- [ ] 초기 심볼 메타는 설정 bootstrap이 아니라 DB seed SQL로 적재
- [ ] 정산 자산은 MVP 5 동안 다중 정산으로 확장하지 않고 `trading.settlement-asset=KRW` 단일 전역 설정으로 고정
- [ ] private order 이벤트도 public 이벤트와 동일한 심볼별 `event_sequence`를 공유
- [ ] private 채널 gap 판정은 채널 전체가 아니라 `payload.symbol` 기준
- [ ] Snapshot source는 live engine 직접 조회가 아니라 `OrderBookCache`
- [ ] WebSocket orderbook 동기화 방식은 전체 Depth snapshot + delta로 고정
- [ ] reconnect 시 버퍼를 비우고 snapshot부터 재요청
- [ ] STOMP heartbeat 기본값 10초 적용
- [ ] private WebSocket 인증은 Phase 5에서 `accountId` 존재/유효성 검증 only

## 2. Outbox / Sequence / Publish

### 2.1 Outbox 저장 및 발행

- [ ] 엔진 결과 반영 트랜잭션에서 `outbox_events` insert와 `symbol_states.last_event_sequence` 갱신을 함께 수행
- [ ] Outbox payload는 `MATCHING_RESULT_BUNDLE { symbol, sequence, trades, orderUpdates, orderbookDeltas }`
- [ ] `trades`, `orderUpdates`, `orderbookDeltas`는 bundle 하위 원소로만 유지
- [ ] `event_type` 기본값은 `MATCHING_RESULT_BUNDLE`

### 2.2 Publisher 경계

- [ ] row claim / 상태 전이는 짧은 DB 트랜잭션 안에서만 수행
- [ ] WebSocket 전송은 반드시 트랜잭션 외부에서 수행
- [ ] DB 커넥션을 잡은 채 Network I/O를 수행하지 않음
- [ ] claim 후 timeout 시 `next_retry_at` 기준 reclaim 가능

### 2.3 실패 / 복구

- [ ] `FAILED`는 재시도 한도 초과 시 부여
- [ ] `FAILED` 발생 시 파이프라인을 정지시키지 않고 다음 sequence 발행 지속
- [ ] 클라이언트는 gap 감지 시 snapshot 재동기화로 정합성 복구
- [ ] Outbox cleanup과 sequence 보존이 서로 독립적으로 유지

## 3. WebSocket / Snapshot 계약

### 3.1 WebSocket Gateway

- [ ] `WS /ws-trading?accountId={accountId}`
- [ ] public topic
  - `/topic/orderbook.{symbol}`
  - `/topic/trades.{symbol}`
- [ ] private topic
  - `/user/queue/orders`

### 3.2 Snapshot / Delta / Gap Recovery

- [ ] `GET /orderbook/{symbol}` 응답에 snapshot 시점 최신 `sequence` 포함
- [ ] client는 WS 수신과 동시에 REST snapshot 요청
- [ ] snapshot 수신 후 `sequence <= snapshotSequence` delta는 drop
- [ ] 이후 delta는 `snapshotSequence + 1`부터 순차 적용
- [ ] gap 감지 시 snapshot부터 재조회
- [ ] private 채널도 `payload.symbol` 기준으로 동일 gap 판단 규칙 적용

### 3.3 운영 제한

- [ ] `send-buffer-size-limit` / `send-time-limit` 초과 시 느린 소비자 disconnect
- [ ] disconnect 시 `ws.slow.consumer.disconnect.count` 증가
- [ ] reconnect 시 기존 버퍼 폐기 후 초기화

- [ ] WebSocket public topic 라우팅/구독 대상이 등록 심볼 기준으로 제한
- [ ] 메트릭 `symbol` tag가 등록 심볼 집합 기준으로 제한

## 5. FOK / IOC 최적화

- [ ] 선형 스캔 대신 O(log N) 자료구조 검토 및 적용
- [ ] 가격 레벨 인덱싱은 `tick_size_rules` 기반 정책과 모순되지 않게 설계
- [ ] 주문 가격 검증은 단일 `tick_size`가 아니라 `symbol + price` 기준 구간별 rule 조회로 수행
- [ ] 일반 LIMIT 주문 insert/cancel 성능 저하 방어
- [ ] replay rebuild 시 동일 집계 구조 복원 가능
- [ ] `PriceLevelDelta`를 `PlaceCalculationResult`, `CancelCalculationResult` 모두에 포함

## 6. 테스트 목표

### 6.1 Outbox / WebSocket

- [ ] 재시작 후 `PENDING` 이벤트 재발행
- [ ] 중복 재전송 무해성 검증
- [ ] lease timeout reclaim 검증
- [ ] fan-out all-or-nothing 재시도 검증
- [ ] snapshot + delta 병합 검증
- [ ] public/private gap recovery 검증
- [ ] heartbeat / reconnect / 느린 소비자 disconnect 검증

### 6.2 성능

- [ ] 1,000레벨 이상 시나리오에서 FOK p95가 Phase 4 기준선 대비 30% 이상 개선
- [ ] LIMIT insert/cancel p95 저하 10% 이내
- [ ] 동일 시나리오 3회 반복 후 중앙값 기준 판정

### 6.3 정합성

- [ ] 기존 Phase 1~4 회귀 및 정합성 테스트 유지
- [ ] bundle fan-out 이후에도 sequence / orderbook / order status 정합성 유지
- [ ] `symbols` 미등록 심볼은 주문 / Outbox / Snapshot / WebSocket 라우팅 대상에서 제외
- [ ] `symbols.status != ACTIVE` 심볼은 신규 주문이 차단되고, ACTIVE 심볼만 엔진이 기동
- [ ] 미등록 심볼의 snapshot 조회는 문서화된 정책대로 일관되게 차단
- [ ] LIMIT BUY / MARKET BUY hold 자산은 항상 전역 정산 자산(`KRW`) 기준으로 계산
- [ ] 가격 구간 경계값에서 올바른 `tick_size` rule이 선택됨
- [ ] `max_price = NULL`인 마지막 tick rule 구간이 정상 적용됨
