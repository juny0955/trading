# Trading Exchange Engine - MVP Phase 5 기획서

---

## 1. 목표

MVP Phase 4에서 구축된 영속성 기반 거래 시스템을 **운영 가능하고 확장 가능한 수준**으로 고도화한다. 특히 이벤트 유실 없는 전송, 정밀한 성능 모니터링, 클라이언트 실시간 인터페이스 구축을 핵심 목표로 한다.

1. **Transactional Outbox 패턴 도입**: 엔진 처리 결과(체결, 주문 상태 변경)를 외부 시스템(WebSocket, 통계 등)에 유실 없이 전달하는 기반 마련.
2. **운영 관측성(Observability) 고도화**: Prometheus/Grafana 연동을 통한 엔진 내부 지연 및 병목 실시간 시각화.
3. **실시간 데이터 스트리밍 (WebSocket)**: 호가창(OrderBook) 및 체결(Trade) 데이터의 실시간 브로드캐스팅 구현.
4. **엔진 알고리즘 최적화**: FOK/IOC 주문 처리 시 발생하는 선형 스캔 비용 최적화.

### 2.1 Phase 5 선결정 항목

구현 착수 전 아래 항목은 먼저 고정한다.

- Outbox 전달 보장 수준: **at-least-once**
- Outbox 소비자(WebSocket 브로드캐스터)는 **중복 이벤트 수신 가능성**을 전제로 idempotent 하게 동작
- **[신규] Outbox 이벤트 단위(Bundling) 정책**: **엔진 커맨드 1건의 처리 결과를 1개의 Outbox Bundle 이벤트로 저장/발행**하는 것을 기본으로 한다. 즉, 개별 `TRADE_EXECUTED`, `ORDER_FILLED`, `ORDERBOOK_UPDATED`를 각각 별도 row로 저장하지 않고, 하나의 `MATCHING_RESULT_BUNDLE` payload 안에 `trades`, `orderUpdates`, `orderbookDeltas`를 함께 담는다. 이를 통해 WebSocket 프레임 수와 클라이언트 Gap 처리 횟수를 줄인다.
- Outbox 발행 순서 보장 단위: **symbol 단위 순서 엄격 보장**. 다중 worker 환경에서도 동일 심볼의 이벤트는 `sequence` 순서대로 브로드캐스트되어야 한다. 이를 위해 특정 심볼의 이벤트는 단일 Publisher Thread가 담당하거나, 송신 직전 sequence 정렬 과정을 거친다.
- Outbox worker 동시 실행 시 claim 방식: 운영 환경(PostgreSQL 등)에서는 `SELECT ... FOR UPDATE SKIP LOCKED`를 사용한다. 단, H2 등 SKIP LOCKED 미지원 DB 환경(테스트)에서는 단순 비관적 락으로 fallback 하거나 단일 worker로 동작하도록 환경별 전략을 분리한다. Worker 장애 시 `next_retry_at` 기반 타임아웃 회수(reclaim) 전략을 사용한다.
- **[신규] 이벤트 순서 보장 기준 (Event Sequence)**: 주문 접수 시 발급되는 `accepted_seq`와는 별개로, 엔진 스레드 내부에서 심볼의 상태(호가, 체결, **주문 상태**)가 변경될 때마다 **심볼별(per-symbol)로 단조 증가**하는 **`event_sequence`를 발급**하여 브로드캐스트의 엄격한 기준점으로 삼는다.
- **[신규] 엔진 재시작 시 시퀀스 복구**: `event_sequence`의 Source of Truth는 Outbox가 아니라 **심볼 메타 테이블(예: `symbol_states.last_event_sequence`)** 로 둔다. 서버 재시작 시 이 값을 읽어 이전 세션의 시퀀스 번호를 끊김 없이 이어서 발급한다. Outbox Cleanup 여부와 무관하게 sequence가 보존되어야 한다.
- **[신규] Private 채널 시퀀스 공유**: 특정 사용자의 주문 업데이트(Private) 이벤트 역시 Public(Trade, Orderbook) 이벤트와 **동일한 심볼별 `event_sequence`를 공유**하여 발급한다. 이를 통해 클라이언트는 Private 메시지를 수신할 때도 통합된 Gap 감지 로직을 사용할 수 있다.
- **[신규] Private 채널 Gap 판정 기준**: `/user/queue/orders`는 account 단위 채널이지만, `sequence`는 심볼별로 발급되므로 클라이언트는 **채널 전체가 아니라 `payload.symbol` 기준으로 sequence 연속성 및 Gap을 판정**해야 한다.
- Outbox payload에는 `event_id`, `event_type`, `event_version`, `trace_id`, `created_at`를 포함
- 주문/체결 이벤트 payload에는 `symbol`, `order_id`, `account_id`(private only), 그리고 엔진이 채번한 `event_sequence`를 포함
- WebSocket orderbook 전송 방식: **초기 snapshot + 이후 delta** (MVP에서는 단일 Depth 옵션인 **전체 Depth** 동기화로 고정한다)
- WebSocket Reconnect 및 Heartbeat 정책: 클라이언트가 연결 끊김 후 재연결 시, 버퍼를 비우고 **반드시 Snapshot부터 재요청**하여 상태를 초기화한다. 또한 **STOMP Heartbeat(기본 10초)**를 필수 적용하여 좀비 세션을 방지한다.
- OrderBook delta에는 반드시 `event_sequence`를 포함하고, 클라이언트는 gap 감지 시 snapshot 재동기화를 수행
- **[신규] Dead Letter (FAILED) 정책**: Outbox 이벤트가 최대 재시도를 초과하여 최종 `FAILED` 처리될 경우, 시스템을 정지(`DIRTY`)시키지 않고 다음 이벤트를 계속 발행(Skip)한다. 클라이언트는 이를 Sequence Gap으로 감지해 자가 복구(Snapshot 재요청)를 수행한다.
- WebSocket 구현 방식: **STOMP(spring-websocket)** 채택. SockJS는 미사용.
- Private WebSocket 채널 인증 방식: **쿼리 파라미터 기반** (`/ws-trading?accountId={accountId}`). 보안 위험을 인지한 Phase 5 내 임시 적용이며, **최소한 DB에서 accountId 존재 여부를 검증**한다. 정식 JWT 인증은 Phase 6으로 defer.
- OrderBook delta 계산 방식: **MatchingEngine 반환값(`PlaceCalculationResult`, `CancelCalculationResult`)에 `List<PriceLevelDelta>` 포함**. delta는 변경된 price level의 (side, price, newTotalQty) 튜플이며, `newTotalQty == 0`이면 해당 레벨 제거를 의미한다. FOK/IOC 누적 수량 캐시 업데이트 시점과 동일 경로에서 생성한다.
- 느린 WebSocket 소비자는 서버가 연결 종료 또는 구독 해제할 수 있다
- **REST 스냅샷 데이터 소스**: 클라이언트의 재동기화 요청 시 매칭 엔진을 직접 호출하지 않고, **`OrderBookCache`에 저장된 최신 상태와 `sequence`를 반환**하여 엔진 부하를 최소화한다.
- FOK/IOC 최적화는 **정확도 우선**이며, replay rebuild 시 동일한 집계 구조를 재구성할 수 있어야 한다

## 3. 핵심 설계

### 3.1 Transactional Outbox 패턴
엔진 결과 반영 트랜잭션 내에 이벤트 저장 단계를 추가하여 **원자적(Atomic) 상태 변경**을 보장한다.

- **흐름**: 
  1. `EngineResultPersistenceService`가 주문/체결/잔고 반영 시 `outbox_events` 레코드를 동일 트랜잭션에 기록.
  2. 이때 동일 트랜잭션에서 심볼 메타 테이블의 `last_event_sequence`도 함께 갱신한다.
  3. 별도 백그라운드 스케줄러(`OutboxPublisher`)가 `PENDING` 상태 이벤트를 claim 하여 전송 대상로 확보한다.
  4. claim 트랜잭션 종료 후, **트랜잭션 외부**에서 WebSocket 브로드캐스터로 실제 전송(Network I/O)을 수행한다.
  5. 전송 성공 확인 후 별도 짧은 트랜잭션에서 `PROCESSED` 상태로 업데이트하고, 실패 시 재시도 가능 상태로 되돌리거나 `FAILED`로 전이한다.
  6. 보관 주기(예: 1일) 경과 후 별도 정리 배치가 `PROCESSED` 이벤트를 삭제한다. (DB Lock 방지를 위해 Chunk 단위 삭제 권장)

- **전달 보장 및 Worker Claim 회수**:
  - DB commit 성공 시 Outbox row는 반드시 남는다.
  - Publisher는 **at-least-once** 전달을 보장한다.
  - claim 상태는 별도 `SENDING` status를 두지 않고, `PENDING + next_retry_at` lease 방식으로 표현한다.
  - Worker가 claim한 row는 일정 시간 내에 처리가 완료되지 않으면, `next_retry_at`을 기준으로 다른 Worker가 다시 claim할 수 있도록 회수(Reclaim) 타임아웃 정책을 적용한다.
  - 브로드캐스트 성공 후 상태 업데이트 전 장애가 발생하면 동일 이벤트가 재전송될 수 있다.
  - 따라서 WebSocket 브로드캐스터 및 downstream consumer는 `event_id` 및 `sequence` 기준 중복 허용/무해 처리 가능해야 한다.

- **트랜잭션 / I/O 분리 원칙**:
  - DB row claim 및 상태 전이는 짧은 DB 트랜잭션 안에서만 수행한다.
  - WebSocket 전송과 같은 Network I/O는 **반드시 트랜잭션 외부**에서 수행한다.
  - DB 커넥션을 잡은 상태로 WebSocket 전송을 수행하지 않는다.
  - MVP 5에서는 별도 `SENDING` status 없이 lease claim으로 구현하고, 핵심 원칙은 **DB TX와 외부 I/O 분리**다.

- **순서 보장 (`event_sequence`)**:
  - 엔진 내부 매칭 루프 안에서 심볼별로 상태가 변할 때마다 단조 증가하는 심볼별 `event_sequence`를 생성해 결과 객체에 담는다.
  - **재시작 시 엔진 초기화 과정에서 DB에 저장된 최신 sequence 번호를 읽어와 상태를 복구한 뒤 발급을 재개한다.**
  - **Public(호가, 체결) 및 Private(주문 상태) 이벤트 모두 이 단일 심볼 시퀀스를 공유한다.**
  - 이 `sequence`가 Outbox 이벤트를 거쳐 클라이언트에게 전달되는 유일한 순서 기준(Source of Truth)이 된다.

- **실패 및 복구 정책 (Skip & Gap Recovery)**:
  - `FAILED`는 재시도 한도 초과 시 부여된다.
  - `FAILED` 이벤트가 발생해도 브로드캐스트 파이프라인을 멈추지 않고(Skip) 그 다음 `sequence`의 이벤트들을 계속 발행한다.
  - 이로 인해 클라이언트 측에는 Sequence Gap이 발생하며, 클라이언트는 규칙에 따라 자동으로 REST API를 통해 Snapshot을 재동기화하여 정합성을 회복한다.

- **운영 파라미터** (`TradingProperties.outbox`로 외부화):
  - `pollingIntervalMs`: Publisher 폴링 주기 (기본값: 100ms)
  - `batchSize`: claim당 처리 건수 (기본값: 50건)
  - `maxAttempts`: 최대 재시도 횟수 (기본값: 3회)
  - `retryBackoffMs`: 재시도 간격 (기본값: 1000ms, fixed interval)
  - `retentionDays`: PROCESSED 이벤트 보관 기간 (기본값: 1일)

- **Payload DTO 정의** (event_version: 1):
  - `MATCHING_RESULT_BUNDLE`: `{ symbol, sequence, trades: [...], orderUpdates: [...], orderbookDeltas: [...] }`
  - `trades` 원소 예시: `{ tradeId, price, quantity, takerSide, buyOrderId, sellOrderId }`
  - `orderUpdates` 원소 예시: `{ orderId, accountId, status, filledQty, remainingQty }`
  - `orderbookDeltas` 원소 예시: `{ side, price, newTotalQty }` (`newTotalQty == 0`이면 레벨 제거)

- **WebSocket Fan-out 정책**:
  - Outbox에는 `MATCHING_RESULT_BUNDLE` 1건만 저장한다.
  - Publisher는 bundle을 읽어 topic별 메시지로 fan-out 한다.
  - `/topic/orderbook.{symbol}`, `/topic/trades.{symbol}`, `/user/queue/orders`로 분해 전송하되, fan-out 하위 메시지는 동일 `eventId`, `symbol`, `sequence`를 공유한다.
  - 하위 topic 전송 중 하나라도 실패하면 bundle 전체 publish 실패로 간주하고 bundle 전체를 재시도한다. (all-or-nothing)

### 3.2 운영 관측성 (Metrics)
Micrometer를 활용하여 Phase 4 TPS 측정 계획에서 정의한 지표들을 실시간으로 수집한다.

- **핵심 지표** (기존: MVP 4에서 구현됨 / 신규: Phase 5 추가):
  - `engine.processing.time` (기존): 순수 매칭 로직 소요 시간 (p50, p95, p99)
  - `engine.queue.wait.time` (기존): 큐 대기 시간 (p50, p95, p99)
  - `order.accept.tx.time` (기존): 주문 접수 트랜잭션 소요 시간
  - `engine.result.tx.time` (기존): 엔진 결과 반영 트랜잭션 소요 시간
  - `end.to.end.order.time` (기존): 요청 수신부터 최종 1차 상태 DB 반영까지의 시간
  - `end.to.end.cancel.time` (기존): 취소 요청 수신부터 취소 결과 DB 반영까지의 시간
  - `engine.backpressure.total` (기존): 백프레셔 발생 횟수 누적
  - `db.lock.wait.time` (기존): DB lock wait 시간
  - `symbol.orderbook.depth` (신규): 심볼별 오더북 가격 레벨 수
  - `outbox.pending.count` (신규): 미발행 이벤트 적체량
  - `outbox.bundle.size` (신규): Bundle 이벤트 1건당 포함된 하위 변화 수
  - `outbox.publish.time` (신규): Outbox 발행 소요 시간
  - `outbox.retry.count` (신규): 이벤트 재시도 횟수
  - `outbox.publish.lag` (신규): 이벤트 생성 시각 ~ publish 성공 시각 지연
  - `outbox.failed.count` (신규): 영구 실패(FAILED) 처리된 이벤트 수 (Grafana Alert 연동 필수)
  - `ws.broadcast.time` (신규): WebSocket 브로드캐스트 소요 시간
  - `ws.active.sessions` (신규): 활성 WebSocket 세션 수
  - `ws.slow.consumer.disconnect.count` (신규): 느린 소비자 연결 종료 횟수

- **대시보드 원칙**:
  - Phase 4 TPS 기준선과 동일한 지표명 또는 매핑 가능한 지표명을 유지한다.
  - 엔진 병목, DB 병목, Outbox 적체, WebSocket fan-out 지연을 한 화면에서 비교 가능해야 한다.

### 3.3 실시간 데이터 스트리밍 (WebSocket)
클라이언트가 폴링(Polling) 없이 실시간 데이터를 수신할 수 있도록 지원한다.

- **Topic 구조**:
  - `/topic/orderbook.{symbol}`: 호가창 스냅샷/델타 업데이트 (전체 Depth)
  - `/topic/trades.{symbol}`: 실시간 체결 내역
  - `/user/queue/orders`: 개별 사용자의 주문 상태 변경 알림 (체결, 취소 등)

- **인증/권한**:
  - public topic은 익명 구독 가능 범위로 유지한다.
  - `/user/queue/orders`는 쿼리 파라미터 `accountId`로 식별하며, Outbox payload의 `accountId`와 일치하는 세션에만 전달한다. (보안 위험을 인지한 임시 허용이며 최소한 DB에서 해당 accountId의 존재/유효성을 검증한다)

- **운영 제한 및 재연결**:
  - 느린 소비자 감지 기준: Spring WebSocket 설정인 `send-buffer-size-limit` (예: 64KB) 및 `send-time-limit` 초과 시 프레임워크가 자동으로 disconnect 처리하도록 구성한다.
  - disconnect 시 `ws.slow.consumer.disconnect.count` 메트릭을 증가시키고 세션을 제거한다.
  - 클라이언트가 네트워크 단절 등으로 재연결(Reconnect)하는 경우, 기존 큐(버퍼)를 모두 비우고 REST API를 통해 Snapshot부터 새롭게 재조회하여 상태를 초기화해야 한다.
  - private 채널은 account 단위 topic이지만 sequence는 symbol 단위이므로, client는 `payload.symbol` 기준으로 gap을 판정하고 해당 symbol 상태를 재조회한다.

### 3.4 FOK/IOC 성능 최적화
현재 오더북의 선형 스캔 방식(`totalAvailableQty` 계산)을 최적화한다.

- **방법 (Trade-off 고려)**: 
  - 단순 누적합(Prefix Sum) 배열은 조회가 O(1)이지만, 호가창 중간에 LIMIT 주문이 삽입/삭제될 때 업데이트 비용이 O(N)이 되어 전체 시스템을 지연시킬 수 있다.
  - 따라서 업데이트 성능을 방어하기 위해 **펜윅 트리(Fenwick Tree) 또는 세그먼트 트리(Segment Tree)**와 같은 O(log N) 자료구조를 검토하여 적용한다.
  - 가격 레벨 인덱싱은 틱 사이즈(tick size) 기반의 배열 인덱스 매핑을 우선 고려한다.
  - 최우선 목표는 **일반 LIMIT 주문의 삽입/취소 성능을 유의미하게 저하시키지 않는 선에서** 가용 수량 조회를 최적화하는 것이다.
- **OrderBook delta 연동**: 누적 수량 트리/캐시 업데이트 시점에 변경된 price level 정보를 `PriceLevelDelta(side, price, newTotalQty)`로 수집하여 `PlaceCalculationResult`, `CancelCalculationResult` 모두에 포함한다.

## 4. 데이터 모델 변경 (Schema)

### 4.1 outbox_events (신규)
| 컬럼 | 타입 | 설명 |
|------|------|------|

| `next_retry_at` | TIMESTAMP | 다음 재시도 가능 시각 |
| `published_at` | TIMESTAMP | 최종 publish 성공 시각 |
| `trace_id` | VARCHAR | 추적용 Trace ID |
| `created_at` | TIMESTAMP | 이벤트 생성 시각 |

- `event_type`은 MVP 5에서 기본적으로 `MATCHING_RESULT_BUNDLE`를 사용한다.
- bundle payload는 public/private 브로드캐스트 시 필요한 하위 이벤트(`trades`, `orderUpdates`, `orderbookDeltas`)를 함께 포함한다.
- **인덱스 권장**:
  - `(status, next_retry_at, event_id)` : Publisher Polling 용
  - `(symbol, sequence)` : 순서 보장 및 조회용
  - `(aggregate_type, aggregate_id, sequence)` : 집계 단위 조회용
  - `(status, published_at)` 또는 `(status, created_at)` : Cleanup 배치의 풀스캔 방지용

| 컬럼 | 타입 | 설명 |
|------|------|------|
| `symbol` | VARCHAR (PK) | 심볼 |
| `last_event_sequence` | BIGINT | 마지막으로 발급된 event sequence |
| `updated_at` | TIMESTAMP | 마지막 갱신 시각 |

- `last_event_sequence`는 Outbox Cleanup과 무관하게 유지되는 sequence의 Source of Truth다.
- 엔진 결과 반영 트랜잭션에서 Outbox insert와 함께 갱신한다.

## 5. API 및 통신 명세

### 5.1 WebSocket 엔드포인트
- **Connect**: `WS /ws-trading?accountId={accountId}`
- **Subscribe (Public)**:
  - `/topic/orderbook.{symbol}`
  - `/topic/trades.{symbol}`
- **Subscribe (Private)**:
  - `/user/queue/orders` (연결 시 전달한 `accountId` scope로 필터링)

### 5.2 Snapshot / Delta 계약 및 병합(Merge) 규칙
REST API와 WebSocket Delta 사이의 Race Condition을 방어하기 위한 강력한 병합 규칙을 정의한다.

1. REST API `GET /orderbook/{symbol}` 요청 시 응답 객체에는 **반드시 현재 스냅샷이 생성될 당시 엔진의 최신 `sequence` 번호**가 포함된다.
2. 클라이언트는 WebSocket 연결 즉시 Delta 이벤트를 큐(버퍼)에 쌓기 시작함과 동시에 REST 스냅샷을 요청한다.
3. 스냅샷(예: sequence=100)을 수신하면, 버퍼에 쌓아둔 Delta 중 **sequence 100 이하의 이벤트는 중복으로 간주해 버리고(Drop)**, 101부터 순차적으로 호가창에 적용한다.
4. 이후 Delta 수신 중 이전 시퀀스 대비 값이 `+1` 이상 커지는 **Sequence Gap**이 발생할 경우 (예: 102 다음 104 수신), Outbox `FAILED`에 의한 누락 또는 네트워크 유실로 간주하고 **버퍼를 비운 뒤 REST 스냅샷부터 다시 요청(초기화)**한다.
5. private order 이벤트는 account 채널로 수신하지만, sequence는 `payload.symbol` 기준으로 해석한다. private gap 발생 시에도 전체 account 상태를 초기화하지 않고 해당 symbol 관련 주문/호가 상태를 재조회해 정합성을 맞춘다.

## 6. 완료 기준 (Definition of Done)

1. **이벤트 보장**: 시스템 장애 후 재기동 시에도 `PENDING` 상태의 Outbox 이벤트가 유실 없이 재발행됨을 확인한다.
2. **중복 허용 정합성**: 브로드캐스트 성공 후 `PROCESSED` 업데이트 전에 장애를 발생시켜도 동일 이벤트 중복 전송이 클라이언트 측에서 `sequence`를 통해 무해하게 처리됨을 확인한다.
3. **병합 및 복구성 검증**: 클라이언트 시뮬레이션 테스트에서 Snapshot과 Delta 간의 Race Condition(스냅샷 요청 중 도착한 구형 Delta)을 성공적으로 필터링하고, Gap 발생 시 스냅샷을 재조회하여 정합성을 스스로 복구함을 확인한다.
4. **실시간성**: 매칭 발생 후 100ms 이내에 WebSocket을 통해 체결 데이터가 전송됨을 확인한다.
5. **가시성**: Grafana 대시보드에서 각 심볼별 엔진 처리 지연, TPS, Outbox backlog, publish lag, FAILED 카운트를 실시간으로 모니터링 가능하다.
6. **성능**: FOK/IOC 최적화(트리 등 적용) 후 **오더북 1,000레벨 이상 시나리오에서 FOK 주문 처리 시간 p95가 Phase 4 기준선 대비 30% 이상 개선**되며, 동시에 **일반 LIMIT 주문의 삽입/취소 처리 시간(p95) 저하가 기존 대비 10% 이내로 유지(Trade-off 방어)**됨을 확인한다. 측정은 **동일 시나리오 3회 반복 후 중앙값 기준**으로 판정한다.
7. **운영 안정성**: 느린 WebSocket 소비자(Send Buffer 초과)가 엔진 처리나 Outbox 발행을 블로킹하지 않고 정상적으로 Disconnect 됨을 확인한다.
8. **정합성**: 기존 Phase 1~4의 모든 회귀 테스트 및 정합성 테스트를 통과한다.
