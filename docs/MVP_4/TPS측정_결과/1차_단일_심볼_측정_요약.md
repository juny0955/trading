# 1차 단일 심볼 측정 요약

## 1. 측정 목적

Phase 4 구현 직후 단일 심볼 주문 부하에서 안정 처리 가능한 TPS 구간과 임계점 진입 구간을 확인한다.

이번 1차 측정은 다음에 집중했다.

* 단일 심볼 `BTC` 부하에서 backlog 없이 유지 가능한 처리량 확인
* queue backlog 발생 시점 확인
* DB/락 병목 여부와 엔진 큐 병목 여부 분리

---

## 2. 측정 조건

애플리케이션/환경:

* Spring Boot `perf` profile
* PostgreSQL 연동
* Prometheus + Grafana 연동
* 심볼: `BTC`

데이터 조건:

* account 100개 seed
* account당 충분한 잔고 주입
  * `KRW 1,000,000,000,000`
  * `BTC 1,000,000`
  * `ETH 10,000,000`
  * `TEST 1,000,000,000`

부하 시나리오:

* k6 `scripts/k6/scenarios/place-single-symbol.js`
* `VUS=1`
* `MIN_PRICE=99,000,000`
* `MAX_PRICE=101,000,000`
* `MIN_QTY=1`
* `MAX_QTY=1`
* `SLEEP_SECONDS` 값을 조정하며 안정 구간과 임계점 구간을 탐색

판정 기준:

* 안정 구간
  * `engine_backpressure_count = 0`
  * `queue_full_rollback_count = 0`
  * `engine_queue_depth = 0`
  * `queue_wait_latency p95` 가 ms 수준에서 유지
* 비안정 구간
  * `engine_queue_depth` 누적
  * `queue_wait_latency p95` 급등
  * `end_to_end_order_latency p95` 급등
  * backpressure 또는 queue rollback 발생

## 3. 주요 측정 결과

### 3.1 안정 구간

대표 안정 구간은 `SLEEP_SECONDS=0.002` 로 확인됐다.

주요 수치:

* `place_order_tps`: `86.69/s`
* `accepted_order_tps`: `86.71/s`
* `trades_per_sec`: `33.04/s`
* `matched_orders_per_sec`: `66.10/s`
* `queue_wait_latency p95`: `4.76ms`
* `engine_processing_latency p95`: `9.45ms`
* `order_accept_tx_latency p95`: `2.44ms`
* `engine_result_tx_latency p95`: `6.71ms`
* `end_to_end_order_latency p95`: `14.99ms`
* `db_lock_wait_time p95`: `1.71ms`
* `engine_queue_depth`: `0`
* `engine_backpressure_count`: `0`
* `queue_full_rollback_count`: `0`

해석:

* 큐 backlog 없이 안정적으로 처리 가능한 구간이다
* DB 락/트랜잭션 지연은 낮은 수준으로 유지됐다
* 현재 환경 기준 안정 처리량은 대략 `85~90 orders/sec` 수준으로 판단한다

### 3.2 비안정 구간

`SLEEP_SECONDS=0.001` 에서는 backlog 누적이 시작됐다.

주요 수치:

* `place_order_tps`: `133.96/s`
* `accepted_order_tps`: `134.02/s`
* `trades_per_sec`: `50.75/s`
* `matched_orders_per_sec`: `101.57/s`
* `queue_wait_latency p95`: `3543.35ms`
* `engine_processing_latency p95`: `7.70ms`
* `order_accept_tx_latency p95`: `1.83ms`
* `engine_result_tx_latency p95`: `4.85ms`
* `end_to_end_order_latency p95`: `3549.24ms`
* `db_lock_wait_time p95`: `1.34ms`
* `engine_queue_depth`: `249`
* `engine_backpressure_count`: `0`
* `queue_full_rollback_count`: `0`

해석:

* backpressure는 아직 발생하지 않았지만 queue backlog가 누적되는 비정상 구간이다
* `queue_wait_latency` 와 `end_to_end_order_latency` 가 함께 급등했다
* `engine_queue_depth` 가 증가했으므로 steady state가 아니라 backlog 누적 상태로 본다

### 3.3 과부하 구간

`SLEEP_SECONDS=0` 에서는 backlog가 더 크게 누적됐다.

주요 수치:

* `place_order_tps`: `205.68/s`
* `accepted_order_tps`: `205.72/s`
* `queue_wait_latency p95`: `15799.50ms`
* `end_to_end_order_latency p95`: `15803.38ms`
* `engine_queue_depth`: `2445`
* `engine_backpressure_count`: `0`

해석:

* queue가 완전히 차지는 않았지만 backlog가 크게 누적되는 과부하 구간이다
* 현재 구조에서 baseline 용도로 사용할 수 없는 수치다

## 4. 병목 해석

이번 1차 측정에서 관찰된 1차 병목은 DB가 아니라 엔진 큐 소비 한계 쪽에 가깝다.

근거:

* backlog 시작 구간에서도 `engine_processing_latency`, `engine_result_tx_latency`, `db_lock_wait_time` 은 낮게 유지됐다
* `db_deadlock_count = 0`
* `db_commit_failure_count = 0`
* `db_rollback_count = 0`
* 반면 `queue_wait_latency` 와 `end_to_end_order_latency` 는 급격히 증가했고 `engine_queue_depth` 가 누적됐다

정리하면 다음과 같다.

* 현재 구조에서는 단일 심볼 입력이 일정 수준을 넘으면 queue backlog가 먼저 누적된다
* DB 락/트랜잭션 병목은 이번 1차 측정 구간에서는 주요 원인으로 관찰되지 않았다

---

## 5. 1차 결론

현재 환경과 시나리오 기준 1차 결론은 다음과 같다.

* 단일 심볼 안정 처리량은 보수적으로 약 `90 orders/sec`
* 약 `130+ orders/sec` 부근부터 queue backlog가 발생한다
* 약 `200+ orders/sec` 구간에서는 backlog가 크게 누적되어 baseline으로 사용할 수 없다

따라서 Phase 4 1차 기준선은 다음처럼 기록한다.

* 안정 TPS 기준선: `약 85~90 orders/sec`
* 임계점 진입 구간: `약 130+ orders/sec`
* 주요 병목 형태: `DB 락`보다는 `엔진 큐 backlog 누적`
